                    模型适配
                    
                  

                  
检查中…

                

              

              

                
                
                
                  群聊回复要快。留空则用上面的模型。
                  重推理模型（如 step-5-preview）实测回一句要 10~30 秒，
                  还会把 token 预算全烧在思考上、正文返回空，不适合放在这里。
                
              

              

                
                
                
                  记忆抽取 / 群复盘 / 表情打标用。这些不在回复链路上，慢几秒无所谓，
                  适合放重推理模型。
                
              



                
                
              

              

                
                
                留空则不修改已保存的密钥
              

              

                
                
                  推理模型先思考再回答，质量更好，但思考量不可控 ——
                  实测同一个模型：普通回复思考 200~330 token（约 3 秒）、
                  记忆抽取 540~730（约 8 秒）、难推理题能烧 1800+ 还不一定想完。
                  所以真正兜底的是下面这几个预算和超时，不是强度参数。
                
              

              

                
                
                注意：部分自建代理会静默忽略这个参数
              

              

                
                
                想超过这个时间就不回了
              

              

                
                
                群聊回复。给紧了思考会把正文挤没
              

              

                
                
                记忆抽取 / 群复盘 / 表情打标 / 看图
              

              

                
                
                  忽略作息时间、发言额度、群冷却与随机放弃，发言门槛降到最低，
                  方便随时验证。不会绕过安全拦截，也不会绕过群开关。
                  打开后页面顶部会常驻一条橙色提醒。
                
              

              

                
                
                  评分本身为 0 的消息（既不相关、也没人叫它）也会被放行。
                  它会接每一句话，会刷屏，只在你盯着的时候开。
                
              


              

                
                

                  
                  
                

                
                
                  不勾选时走完整链路：决定层判断该不该说 → 人设 prompt → 模型 → 去 AI 味。

打字节奏

              —
            

            

              

                
                  拟人的关键：真人不可能秒发。一条消息的耗时 = 反应时间（看到消息到开始打字）
                  + 每个字耗时 × 字数，每条气泡各算一次。表情包按"点一下就发"算，不按字数。
                
              

              

                
                
              

              

                
                
                手机上打中文约 250~500ms/字；180 已经算手快的
              

              

                
                
                再短的消息也至少等这么久（打「在」也要拿起手机）
              

              

                
                
                再久就不像打字慢，像掉线了
              

              

                
                
              

              

                
                
                0.4 秒就回一句「在」太快，像自动应答
              

              

                
                
                  应保持开启。关掉后第一条只有反应时间就发出去了 —— 曾经就是这样，
                  「在」两个字 0.4 秒到群里，一眼假。

OCR / 看图

              —
            

            

              

                
                
                
                  NapCat 自带的 OCR 同步秒回但只有纯文字；
                  PaddleOCR-VL 输出 markdown（公式变 LaTeX、表格保结构），
                  但实测快则 6 秒、慢则 94 秒，所以它永远在后台跑，结果按图缓存。
                
              

              

                
                
              

              

                
                
                  关闭时只有 NapCat 的快速 OCR。开启后按上面的后端策略工作。
                
              

              

                
                
                留空则不修改；填入后会自动写进 .env 的 PADDLEOCR_TOKEN
              

              

                
                
              

              

                
                
              

              

                
                
              

              

                
                
                太小的图（表情包）不值得送云端
              

              

                文档增强（拍照/扫描件才需要，开了更慢）
                

                  
                  
                  
                

              

            

          


          

            

              
网络搜索

              —
            

            

              

                
                
                  给模型补上"知识截止之后"的信息。关键不是能不能搜，而是什么时候该搜 ——
                  每条消息都搜既慢又蠢，所以有独立的时效性判定，
                  只有「今天/最新/多少钱」这类明确的实时信息需求才触发，被点名问时阈值放宽。
                
              

              

                
                
                各家请求体形状不同，已分别适配；generic 用宽容解析兜底
              

              

                
                
              

              

                
                
                留空则不修改；填入后会自动写进 .env 的 SEARCH_API_KEY
              

              

                
                
              

              

                
                
                搜索挂在回复链路上，慢了这个回复就不像人了
              

              

                
                
                越高越少搜。0.5 = 命中一个时效词加疑问句才搜
              

              

                
                
              

              

                
                
              

              

                
                
              

              

                
                人家专门点名问了，含糊回答很减分，所以值得多搜一点
              

              

                
                

                  
                  
                

                走真实请求，用来确认 key 和字段对不对
